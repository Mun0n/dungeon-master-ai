# Architecture

One Android application module, `:app`. A second module waits until something other than this app needs the rules.

## Packages

- `com.dungeonmasterai.domain` holds characters, dice, game state, the keyword parser, and `GuardiansBridgeEngine`.
- `com.dungeonmasterai.domain.adventure` holds the generic adventure document, its validator, `AdventureState`, and `AdventureEngine`. The bridge screen does not call it.
- `com.dungeonmasterai.presentation` holds the Compose UI, `GameViewModel`, `AdventureSession`, and the provisional Valdumbría screen. The public menu lists published adventures. The only one is Las campanas de Valdumbría. The Guardian's Bridge stays in the module and in its tests, and the menu does not open it. The bridge screen still does not call `AdventureSession`.
- `com.dungeonmasterai.data` holds `SavedGameStore`, `AdventureGameStore`, `Narrator`, `AdventureBackend`, and their implementations. The domain does not implement those interfaces.

`domain` must not import Android or Compose. `DomainBoundaryTest` fails the build if it does.

## Who writes the state

`GameViewModel` stores a `StateFlow`. It creates the opening state, parses free text, and calls the engine. It does not roll dice and it does not change health, inventory, or outcome.

`GuardiansBridgeEngine.resolve` is the only writer of those three fields on `GameState`. A rejection appends `ActionRejected` and leaves them as they were. Suggested buttons and the parser both produce a `PlayerIntent`, including `Unrecognized` and `Ambiguous`, so the engine records every rejection the same way.

`Die` is a port. The screen uses `RandomDie`. Tests use `ScriptedDie`. `SavedGameStore` persists the `GameState` the engine returned and restores it when the process starts again. A corrupt snapshot is dropped, and character creation shows. A failed save leaves the in-memory state in place.

`AdventureGameStore` is a second port. It persists one confirmed `AdventureState` and does not persist `GameState`. The two saves do not replace each other. A failed adventure write leaves the previous adventure commit in place. The bridge screen does not call this port. `AdventureSession` does.

`Narrator` is a port in `data`. It returns a raw payload. `parseNarratorPayload` accepts only a JSON object whose string fields are `narration` (at most 400 characters) and `intent` (`PERSUADE`, `PAY`, `ATTACK`, `UNRECOGNIZED`, or `AMBIGUOUS`). Anything else, including extra fields, is unusable. The parser is local: `org.json` is stubbed on the JVM tests. `GameViewModel` then calls the engine with that narration and that intent. The engine writes the narration only when it accepts the transition. A null narrator, a thrown call, or an unusable payload uses `KeywordIntentParser` and the scene's fixed lines. A reply that arrives after a newer action is dropped. `HttpNarrator` POSTs to `narrator.baseUrl` from `local.properties` and sends no API key. An empty URL leaves the narrator absent. Suggested buttons do not call it. That bridge contract is unchanged.

The FastAPI process in `backend/` is a separate, stateless service. `POST /v1/interpret` returns a status and either a candidate action or, when the status is `CONCLUSION`, one option for each offered claim. `POST /v1/narrate` describes a resolution the caller already confirmed. `POST /v1/scenes` returns prose only when the caller sets `generationRequired`. A response has no effect list and no next `GameState` or `AdventureState`. The prompt is built from the authorized view in the request: visible characters, available actions, revealable lines, the summary, recent lines, and, when a deduction is eligible, the claim prompts and option glosses. That offer does not include the accepted values, the contradiction pairs, or the solution statement. The narration and scene prompts are a prose projection of that request: the location name, character names, the purpose, revealable lines, other revealed sentences, a redacted summary, recent lines, and, for narration, the outcome in words (`completed`, `not completed`, or `rejected`), a stored check in Spanish words, the life after the resolution, and the Spanish ending title when an ending is already stored. The request still carries the action id, the outcome, the check, and the applied effects so the service can validate the call. Those ids are not copied into the narration or scene prompt. Interpretation still receives action ids so it can map a sentence, and it does not receive unrevealed evidence text or the solution statement. When the request sets `narrativeLanguage` to `es`, narration and scene instructions ask for natural Spanish in the second person and the present tense, with mystery and dread, and tell the model not to invent a canonical fact. Interpretation stays a mapping instruction. A request without the language field keeps the previous instruction. The bridge narrator is a separate client and does not send this field. An empty `narrativeSummary` auxiliary is omitted. A narration request uses the scene contract that authorized the resolution, so a later move or ending does not block that narration. The prose location, purpose, and revealable lines are those of the place that resolution left the player in, and the narration also sends the confirmed clock as `hora` and the outcome prose as `hecho`. Those facts are ordered ahead of the summary. The narration instruction keeps the clock, the life, and the check as context and tells the model to describe what the character does or experiences, not to recite the hour, the life total, the die, or the difficulty. Finding a path is not the same as moving into the place. `location` stays the only confirmed place. The adventure client refuses an action that contract does not list before it calls the engine. Undiscovered evidence, future branches, and unapplied effects have no field on that request. `forbiddenInformation` on a call is the active list. A phrase leaves that list only when a revealed source already authorizes it. Elia's death leaves the list when `evidence_elia` is held, including on the narration of the resolution that granted it. "Elia sigue viva", a real crypt creature, and a second midnight never leave the list. The adventure document on disk is unchanged. The service still applies a case-insensitive substring check to the list it receives and does not learn the evidence ids. On the way out, a copy of the summary is redacted by sentence, then a follower that only makes sense because of a dropped sentence is dropped. On the way back, the same two passes clean `narrativeSummary` before the forbidden check. If the narration text still contains an active secret or a technical token, the reply is unusable and the previous summary stays. If the text is clean, one bad summary sentence does not discard it. Player-visible narration, generated scene text, and summary sentences also reject an identifier that contains `_`, an effect type name, and a fixed list of bare tokens matched as whole words. `plaza` is not on that list. This is not a guarantee that the prose understood the story. A paraphrase can still carry a secret. Groq's HTTP 400 body `Failed to validate JSON` is invalid model output and uses the one existing retry. The provider body is not attached to the correction or the player notice. A timeout is not retried. Android makes one call for the action. An interpretation failure before the commit does not resolve. A narration failure after the commit keeps the roll and the effects. Restoring an awaiting narration does not resolve again. Authored `localProse` is shown when the model text is unusable, including when that authored line contains a forbidden phrase. Player text is at most 500 characters, action narration at most 1,200, generated scene text at most 2,000, and the narrative summary at most 3,000. `AdventureSession` calls this service. `HttpAdventureBackend` reads `adventure.backendUrl` from `local.properties`. An empty value leaves the client absent. The app sends no API key. A release build rejects an `http` URL. A debug build may use `http` for the local addresses in [backend/README.md](../backend/README.md). `narrator.baseUrl` stays the bridge narrator and is not this service.

Clue ids, flag names, action ids, claim ids, option ids, and effect type names are engine data. Narration, the narrative summary, and generated scene text are replaced when they contain an identifier with `_`, an effect type name, or a bare token from the fixed list, matched as a whole word. `plaza` stays. The design in [MILESTONE_11_DESIGN.md](MILESTONE_11_DESIGN.md) is approved. Its implementation is in progress and is not marked complete. A token check still cannot prove tone, and a paraphrase can still state a secret. A free-text conclusion is the only player path into `AdventureEngine.deduce`. The session calls it inside `commitIfCurrent` only after the claim values match and the evidence is still held. The accepted line is the deduction's authored prose, stored `VALIDATED` in that same transaction. A rejected conclusion writes nothing. `choose` never calls `deduce`.

`AdventureSession` keeps one turn at a time for its own caller. `AdventureGameStore.commitIfCurrent` is the shared lock: it reads the stored revision, calls `AdventureEngine.resolve` or `AdventureEngine.deduce`, and writes the new state in that same lock. A second turn whose revision is no longer current does not resolve and does not write. Dice and effects happen only inside that call. The session publishes a narration string only after that string has been committed as `VALIDATED`. A deduction's prose is written `VALIDATED` in the deduction transaction, so restoring it does not roll and does not call the model.

Every successful commit of an existing adventure advances `stateRevision`. That includes validated narration and generated scene prose, not only a rules change. The compare-and-set is that integer. A session that still holds the previous integer does not write. The token stored on the pending narration stays the revision of the resolution that produced it. A reply is matched against the token sent with that request.

A revision conflict reloads the confirmed record and replaces the session snapshot with it. The attempt that lost is not stored. A new game that loses leaves that character unsaved and shows the game already in the store. An action that loses does not roll and does not create a pending narration. Narration prose that loses is discarded. If the confirmed row is still awaiting, the player can retry it. If it is already validated, that stored text is shown. Scene prose that loses is discarded. Prose already stored for that contract is shown. A required scene that is still missing stays paused so the player can retry.

The delivery guarantee is the database transaction, not the moment the screen draws. Before `commitIfCurrent` returns, a crash restores the previous adventure state. The roll was not confirmed and may be rolled again. After it returns, the effects, the clock, and the attempt are durable. A crash while the narration request is in flight leaves the row `AWAITING`. The next launch shows the confirmed state and does not roll again. It also does not call the model until the player retries narration. A crash after the validated narration transaction and before the session copies that text into memory is closed by the next launch: the stored text is shown and the model is not called again. A reply that reached the process but was not committed is gone. Retrying narration can produce different prose. It cannot repeat the roll or the effects. A reply is used only when its `requestId`, `stateRevision`, and `sceneContractId` match the call that is still current.

The screen's calls to `start` and `choose` update the `StateFlow` on the caller thread. `submitText` does too when no narrator is wired. With a narrator, that call runs in `viewModelScope`. Loading and saving do as well. Nothing in the rules needs a coroutine. The bridge screen still uses that path. It does not call `AdventureSession`.

`MainActivity` starts on the Unwritten menu. The menu reads the adventure save. "Nueva partida" deletes that snapshot only after confirmation, and does not delete the bridge save. The bridge screen remains in the module and is not opened from this menu. The Valdumbría branch reads `assets/adventures/valdumbria.json`, decodes it with `loadAdventure`, and gives that document to `AdventureEngine` and `AdventureSession`. The asset read stays in the activity. `domain` still does not import Android. The two saves stay on one database and do not replace each other. Room is at version 6. Migration 3 to 4 adds `relevantFacts` on `adventure_attempt`. Migration 4 to 5 adds character presentation. Migration 5 to 6 adds `adventure_hypothesis`. None of those migrations alter the bridge tables. A save from version 5 restores with an empty hypothesis list. A failed attempt from an older save has an empty projection and stays closed. The plaza and tavern contracts list the investigation actions for those places. The session still refuses an action the current contract does not list. `inesClockLine` reads Inés's confirmed state. A protection flag set by the action that crosses midnight does not change the line into a rescue, because the midnight event has already set her state.

`AdventureEngine` is a second writer, for `AdventureState` only. It never writes `GameState`. A rejection returns the same `AdventureState` instance. A resolved action, including a failed check, applies that action's time cost, then the midnight event when this action crosses it, then one closed list of effects. The first ending stops every effect still pending in that resolution. `AdventureResolution.Accepted` lists the effects that actually ran, in that order, and omits everything after the stop. The list is the sealed type `Effect`. The JSON names a type. It does not carry code. Schema version 1 is decoded with Kotlinx Serialization and then `validateAdventure`. Unknown fields and unknown effect types are rejected. The clock is not an effect. The engine adds `timeCostMinutes` only after the action resolves, and it fires the midnight event once when the count crosses 120 minutes from 22:00. A prologue passage is not an action: the engine marks the next unread passage without rolling, spending time, or changing life, and a save that already has history does not enter it. Scene contracts are stored on the document and are not read during resolution. `localProse` on an outcome and `generationRequired` on a scene contract are narrator data. The engine ignores both. `freeAction` is client data on that same contract, and the engine ignores it too. The Valdumbría screen shows at most four featured actions for the current situation. The interpreter still receives every available action. A written action opens only when that contract allows it, or when a conclusion is offered. The bridge keeps its three intents, and its written action opens from the same secondary choice while the scene is ongoing. A location has at most one scene contract. Tests load a fixture from the test classpath. The app does not ship that fixture. The app does ship `assets/adventures/valdumbria.json`. Room version 3 keeps the bridge tables and adds a separate adventure slot. One transaction replaces that slot: character, inventory, clock, midnight, flags, discoveries, evidence, clues, relationships, NPC state, attempts, fired events, deductions, history, ending, the narrative summary, and `stateRevision`. The same transaction stores the pending narration, accepted scene prose, and the recent lines. The summary stays empty until a narrator writes it, and a value already on the state is kept through resolution. The death ending id and the midnight event id are stored with the snapshot. A load rejects a death ending unless health is 0, health 0 unless that ending is set, and a midnight flag that does not match the fired event. A corrupt adventure snapshot is deleted. The bridge snapshot stays. A corrupt pending narration is deleted and the confirmed adventure state stays, so a broken narration row cannot cause another roll. The effect list and the document shape are in [ADVENTURE_SCHEMA.md](ADVENTURE_SCHEMA.md). The numbers are in [GAME_RULES.md](GAME_RULES.md).

## Sound

Background music is a looping `MediaPlayer` in `presentation`. `DungeonMasterApp` owns that player for the process. `MainActivity` starts it in `onStart` and pauses it in `onStop`, so the Unwritten menu and the adventure share one loop. A configuration change does not pause it. Leaving the app does. The domain does not select tracks and does not import Android audio types. The shipped track is `res/raw/b_minor_arpeggio.mp3`. A later track would be chosen by the screen from the confirmed situation and played by this same player.

## Screen orientation

Every screen is designed for portrait. That includes the game picker, character creation, The Guardian's Bridge, Valdumbría, and the inventory, journal, dialogue, and settings screens when those exist. There is no landscape layout.

The manifest sets `android:screenOrientation="portrait"` on the activity, and `android:windowSoftInputMode="adjustResize"`. It does not set `android:appCategory`. It does not set `android.window.PROPERTY_COMPAT_ALLOW_RESTRICTED_RESIZABILITY`.

The app targets API 37. On a display whose smallest width is below 600dp, `android:screenOrientation="portrait"` on the activity is honored. On a display of at least 600dp, Android ignores a portrait lock for an app that targets API 37, in full screen and in multi-window. The manifest property `android.window.PROPERTY_COMPAT_ALLOW_RESTRICTED_RESIZABILITY` is a temporary opt-out for API 36 and does not restore the lock at this target. The platform also exempts an application marked with `android:appCategory="game"`. This app does not set that category. Milestone 10 checked the phone lock on `dm_phone`, smallest width 411dp. The activity stayed portrait. The large display checked in the same milestone was `spider_tablet`, 1920×1200 at 240 dpi, smallest width 800dp. After a landscape rotation the activity stayed in a centered portrait window, `ComposeView` bounds `[510,0][1410,1200]`. It did not stretch into a landscape layout. The platform description is the Android 16 behavior change for orientation, resizability, and aspect ratio.

## What is deliberately missing

Hilt: one ViewModel for the bridge, and one for the provisional adventure screen. `DungeonMasterApp` owns the database, the bridge narrator, the background music, and the optional adventure backend. `MainActivity` passes a factory for each screen. The bridge narrator payload stays on `parseNarratorPayload` because it is two string fields. Adventure documents use Kotlinx Serialization. The bridge screen still uses the bridge store. `AdventureSession` is shown only on the Valdumbría branch.

The narrator proposes narration and an intent. The engine still accepts or rejects the transition. The model never returns the next `GameState` or the next `AdventureState`.

## Build

AGP 9.3.1 with built-in Kotlin, raised to Kotlin 2.4.21 from the root `buildscript` classpath. The Compose compiler plugin and the serialization plugin match that Kotlin version. Room is compiled with KSP. `org.jetbrains.kotlin.android` is not applied. `kotlinx-serialization-json` 1.11.0 decodes adventure documents.

`compileSdk` is API 37 minor 0 because the installed platform directory is `android-37.0`. `minSdk` is 26. JDK 17.
